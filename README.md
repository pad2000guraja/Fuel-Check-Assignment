# Fuel-Check
This group project focused on building a real-time data engineering pipeline that leveraged APIs to collect, process, and visualise live fuel price information from the New South Wales FuelCheck API. The application continuously ingested fuel price updates, processed the data efficiently, and displayed real-time fuel station information on an interactive map through a Streamlit dashboard.

# Project Features: 
1) Retrieved live fuel price data from the NSW FuelCheck API.
2) Processed and cleaned incoming data using Python and Pandas.
3) Published only modified records through MQTT, reducing unnecessary network traffic and improving pipeline efficiency.
4) Developed an interactive Streamlit dashboard with Folium maps to visualise fuel station locations and current fuel prices in real time.
5) Implemented a scalable pipeline capable of handling continuous API updates.

# Implementation Phases 
## Data Retrieval 
The first stage in our pipeline is data retrieval. We created a specialized class called FuelDataClient. This class is responsible for handling all communication with the NSW FuelCheck API. Moreover, this class consists of two methods: get_access_token and fetch_data and receives client_id and client_secret as parameters.  
To elaborate further our first method, get_access_token, was developed to request an access token from the API since it requires OAuth2 for access. This method combines the client ID and secret and encodes them using Base64 and includes the encoded values in the request header. Afterward, the subject function calls requests.get using endpoint (/oauth/client_credential/access token) and passes the necessary headers and 
parameters to obtain the access token.  
The second method fetch_data was designed to fetch target data from the API. This method initiates a GET request to the primary endpoint (/FuelPriceCheck/v1/fuel/prices) and the request includes the access token and required headers, such as apikey, transactionid, and requesttimestamp. The response from this endpoint is in JSON format and contains two key parts: 
  • Station metadata: contains information like station name, brand, full address, and GPS coordinates (latitude and longitude). 
  • Fuel prices: include the price, fuel type, station code, and the timestamp that represents the last time the data was updated. 
We used pandas.json_normalize to convert the nested JSON into two separate Pandas DataFrames, one for stations and another for prices, which makes the data easier to process and integrate later in the pipeline. In addition, we introduced significant enhancements to optimize overall performance and data retrieval process. This enhancement is realized by leveraging (/FuelPriceCheck/v1/fuel/prices/new) to fetch fuel price records updated since the last retrieval call. Subsequently, this approach minimizes latency and significantly offloads resource consumption to handle minimal API calls efficiently, exercising software engineering best practices in action.  

## Data cleaning and Integration 
The second stage in our pipeline is data cleaning and integration. We started this phase by renaming relevant columns in the station data frame by assigning meaningful names to assist in further cleanup steps. Accordingly, we changed "name" to "station name," "location.latitude" and "location.longitude" to "lat" and "lon" respectively. Also, we renamed "code" to "station code" to enhance clarity and consistency with 
the price data since it is the shared column between both station and price sets. Afterward, we then dropped all rows that had missing values in latitude and longitude fields. Also, we validated and parsed the "lat" and "lon" columns to numeric values and removed invalid and missing records 
that may influence the reliability of data published on the dashboard. In addition, we cleaned the prices data by converting the prices to numeric values and filtering out rows with invalid entries such as prices with negative entries. Afterward, we coordinated sorting prices data by the "last updated" column and grouped it by both "station code" and "fuel type." Hence we retained only rows with the most recent update.  

This allowed us not only to reduce noise but also to focus on the latest fuel prices for each station and fuel type. Additionally, extreme data points and outliers were addressed by filtering out all records with negative and invalid values to retain reasonable value pairs for each station and fuel type pair. Following this approach, we discard outdated and anomalous data points and reach realistic fuel prices across all stations. 
To finalize our cleanup activities, we merged the latest prices data with the cleaned station data using "stationcode" as a mutual field and arrived at the final clean data structure to maintain in our pipeline. In closure to this phase, these implemented approaches allowed us to create a single integrated data frame containing both station data and fuel price information. 

## Data Publishing via MQTT 
The third stage in our pipeline is publishing the price data to our dashboard system using the MQTT protocol in real time. To accomplish this task, we used the public broker “broker.hivemq.com” and published all messages under the topic “fuel/new_prices”. Also, to establish a connection to our broker, we utilized paho.mqtt client to listen for new messages and maintain asynchronous publishing. 
Furthermore, to enhance our process, we developed the publish_if_changed function to ensure that only updated or new fuel prices are published to the broker. This optimization is a key enhancement to prevent duplicate messages from being sent, which helps reduce bandwidth consumption and minimizes traffic to our dashboard by sending only the necessary updates. 
Moreover, we implemented several additional optimizations to improve performance. First, we used MessagePack (msgpack.packb) to publish our data in a compact binary format, which reduces payload size and enhances transmission speed. We also introduced a short delay (time.sleep(0.1)) between messages to lower the load on the broker, allowing the subscriber in the dashboard to process each message more 
efficiently. 
In addition to the above enhancements, our continuous implementation constantly fetches updated data using the fetch_data method of FuelDataClient from the API. Similarly, the subject function then cleans and merges the updated data using the clean_and_merge() method, then switches to call 
“/FuelPriceCheck/v1/fuel/prices/new” to retrieve data changes of new fuel prices every 60 seconds which considerably minimizes the number of program API calls, retrieved data records, and overall overhead on computing resources to maintain dashboard. 

## Subscribing and visualization 
The visualization system is built around a message-driven architecture that enables seamless real-time updates from the publishing module. The subscriber establishes an MQTT connection using the Paho client and listens to the fuel/new_prices topic. Incoming messages, encoded in MessagePack for compact transmission, are decoded upon arrival and placed in a queue. This queue ensures that the message ingestion process is decoupled from the user interface, preserving performance even under high update frequency. Each decoded message contains details such as station ID, brand, location, fuel type, price, and last updated timestamp. These records are integrated into a persistent in-memory store using st.session_state, which maintains the dashboard's state across Streamlit reruns. The station data is structured hierarchically, allowing each station to hold multiple fuel types without conflict or redundancy. The dashboard employs a Folium map to display markers for fuel stations, where every marker is rendered dynamically and linked to a popup containing the station’s name, address, and detailed table of fuel prices. A dropdown filter allows users to focus on a specific fuel type. The map interface preserves its zoom level and selected filters across automatic 15-second refresh cycles, offering a stable and responsive real-time experience. This design supports continuous updates without interrupting user interaction and ensures that only updated information is visualized incrementally, avoiding unnecessary redraws. 

## Continuous Execution 
This system is designed to run continuously without the need for any manual triggers. Once initiated, it will keep executing in the background retrieving updated fuel prices every 60 seconds using /fuel/prices/new endpoint and conducting cleanup, data merging, and publishing operations continuously. In this approach, we ensure that the system stays active and automatically handles your updates as they arrive. Needless to say, this integration with MQTT and implementation of an asynchronous publishing loop suppose this realistic, continuous flow and ensures that our dashboard remains responsive, consistent, and reliable and delivers real-time data.
